## 性能记录与容量限制

当前固定步仍为 50 ms。一倍速平均模拟预算约 50 ms/步，2× 约 25 ms，5× 约 10 ms；单个重步超过预算时，Worker 只能隔离主线程阻塞，不能保证模拟满速。CPU/GPU 总负载低也不能证明帧时间充裕：串行热点、任务调度与 Canvas 栅格化/合成仍可阻塞画面。F3 的绘制耗时是 JS 提交，不包含全部 GPU 进程与呈现时间；判断流畅性还需实际帧间隔和长帧。

## 后续优化与框架选择

现有实现仍有可识别的算法与数据布局优化空间，尚不能把最大规模卡顿归因于“框架已到上限”。先在相同种子、相同实际交战状态和同一设备定位慢项，再决定迁移范围；提高模拟频率、增加 Worker 数量或直接换引擎都不能自动消除重复扫描。

1. 核对实际 DPI/视野下的缓存命中、帧间隔、栅格化与合成；在相同 CSS 视野下比较 DPR 1/1.25/1.5/2，避免把 JS 提交当完整绘图耗时。
2. 优化选敌候选规模、重复邻域查询、遮挡复验与碰撞活动集合，再调整数据布局；必须保留远处后备实际参战、实体阻挡和确定性。
3. 用相同状态重新测量 4×/8× 模拟吞吐、实际倍速、帧 P95 与长帧；只保留可追溯的报告，不以暂停或小场景代替完整交战结论。

2026-11-04 已评估的迁移方向如下，均尚未完成同场景移植基准，也未据此引入新引擎依赖：

| 方向 | 适用范围与限制 | 既有评估依据 |
| --- | --- | --- |
| 浏览器显示层改为 PixiJS | GPU 批绘制可减少逐模型 Canvas 调用；保留输入/模拟接口，但不能单独解决超预算的模拟步 | [渲染循环](https://pixijs.com/8.x/guides/concepts/render-loop)、[性能说明](https://pixijs.com/8.x/guides/concepts/performance-tips) |
| 原生桌面 Bevy/Rust ECS | 面向 8× 及更大规模的候选；可评估数据布局、独立阶段并行与实例化显示，迁移工作量最大 | [ECS](https://bevy.org/learn/quick-start/getting-started/ecs/)、[并行查询分批](https://docs.rs/bevy/latest/bevy/ecs/batching/struct.BatchingStrategy.html)、[精灵压力示例](https://bevy.org/examples-webgpu/stress-tests/many-sprites/) |
| Godot + GDExtension/C++ 模拟 + MultiMesh | 适合需要编辑器的方向；密集模拟应评估原生扩展和批量显示，不能原样变成每兵模一个脚本节点热点 | [MultiMesh](https://docs.godotengine.org/en/stable/tutorials/performance/using_multimesh.html)、[线程接口](https://docs.godotengine.org/en/stable/tutorials/performance/thread_safe_apis.html) |

兵种数值与四套军队仍为本作初稿，未按费用配平。[旧对抗报告](balance.json)是 8 组 × 3 种子、45 秒上限的历史样本；后续动作、士气、规模和戟兵防御已修改，不能沿用旧胜负判断当前强弱。批量脚本现在使用 4× 编制，重跑后仍需区分超时与平局，并加入费用、地形与操作变量才能评估竞技平衡。单体目标数、动作与伤害预算仍需结合观感讨论，不能把初版取舍当成已经逐项定稿。

RL 对战 AI 保留后续阶段：先稳定机制与规则 AI 基线，再设计 observation/action/reward 接口和自博弈评估。复杂地形与全局寻路、原作完整单位/弹药数据库、逐动画接敌与击倒、飞行、炮兵、攻城、魔法和种族系统均未完成；待办入口在 [TODO.md](../TODO.md)。自动回归有助于快速排错，动画可读性、操作手感、竞技平衡和原作隐藏行为仍需有目标的人工验收。
