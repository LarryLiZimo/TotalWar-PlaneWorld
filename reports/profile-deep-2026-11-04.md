# 最大规模会战：真实浏览器与 Worker 深度 Profile

2026-11-04。结论：**“PPT”的直接主因已在真实浏览器复现为 DPI 导致精灵缓存失效，进而堵塞 Canvas 的 GPU 进程栅格化路径。模拟线程另有持续超预算的问题。** 单独优化近战遮挡检查不能解决这两个层面的总开销。

本轮实际采集了浏览器主线程、独立 Worker 和打包后 Node 模拟的 `.cpuprofile`，以及包含 GPU/Skia/Canvas 栅格化事件的 Chrome Trace；显示结果来自真实 Canvas，不是模拟上下文调用计数。诊断在冻结副本内完成，正式业务源码未修改。

## 1. 完全暂停战局也只有 3～4 FPS，直接定位渲染问题

条件：本机 Windows，Chrome 156.0.8078.80 无头模式，真实 ANGLE/D3D11 + Intel Iris Xe；Chrome 报告 2D Canvas、GPU 合成和栅格化均启用。1600×900 CSS 视口，经典步射对经典步射、8×、种子 20261104，6,368 模型。固定在同一个第 20 秒战斗状态，暂停全部模拟，仅改变 DPR。

| 条件 | 实际 rAF FPS | 帧间隔 P95 | JS 内测得的 render 提交 |
| --- | ---: | ---: | ---: |
| DPR 1，原缓存路径 | **59.7** | 25.0 ms | 12.1 ms/帧 |
| DPR 1.25，原矢量路径 | **3.4** | 398.8 ms | 23.1 ms/帧 |
| DPR 1.5，原矢量路径 | **3.9** | 274.4 ms | 20.5 ms/帧 |

这里没有 AI、碰撞、近战或 Worker 模拟负载，严重掉帧仍然存在。

代码链条：

1. `src/main.ts:67` 按 `devicePixelRatio` 放大画布尺寸。
2. `src/main.ts:417` 和 `src/camera.ts:27` 用物理画布尺寸计算 `camera.zoom`。
3. `src/render.ts:379` 使用 `camera.zoom <= 4` 决定是否缓存。
4. 相同视野的 zoom 从 DPR 1 时 3.44，变成 DPR 1.25 时 4.30、DPR 1.5 时 5.17，关闭已有缓存，逐兵调用矢量绘制。

这不只是绘制 API 数量增多的推断：实际掉帧已复现。

## 2. GPU/Skia Trace 找到了被性能面板漏掉的主要耗时

原性能面板在 `render(...)` 返回后就停止计时，只覆盖 JS 提交 Canvas 命令的同步时间。后续命令解码、栅格化、GPU 服务与 flush 没有算进去。

对暂停、DPR 1.5 的相同画面，另取 8 秒完整 GPU/Skia Trace：

| GPU 进程主线程事件 | 窗口内累计时间 | 次数 | 单次最大 |
| --- | ---: | ---: | ---: |
| `RasterDecoderImpl::DoRasterCHROMIUM::Deserializing` | **2,434.9 ms** | 130 | 62.0 ms |
| `RasterDecoderImpl::DoEndRasterCHROMIUM::Flush` | **5,517.2 ms** | 130 | 147.3 ms |
| GPU 主线程外层任务 | **8,020.4 ms** | 679 | 209.3 ms |

前两项是不同阶段，合计约 7.95 秒，解释了该窗口内 GPU 服务路径几乎持续被占据。外层任务包含前两项，不能再相加。此处是任务持续时间，不把它等同于 GPU 硬件利用率。

JS 主线程 CPU profile 此时约 90% 为 idle，且 JS 提交仍只需约 20 ms；低 JS 占用并不代表画面有实时余量。大量逐模型路径在 GPU 进程内执行，浏览器的绘图调度受其拖累，rAF 实际间隔达到约 0.3 秒。

### 保持相同 DPR 和画面的受控验证

只在诊断副本增加强制走原精灵缓存的开关，两组均暂停在同一状态、DPR 1.5、同一视口，并开启相同的原生事件追踪：

| 条件 | FPS | 帧 P95 | 每帧 JS 提交 |
| --- | ---: | ---: | ---: |
| 原矢量路径 | **3.27** | 332.5 ms | 19.64 ms |
| 恢复精灵缓存 | **58.37** | 24.9 ms | 12.19 ms |

约 **18 倍显示帧率差异**。缓存组 GPU 端 flush 累计约 579 ms，单次最高 1.73 ms；原组累计约 5,517 ms，单次最高 147.3 ms。GPU 服务外层最长任务从 209 ms 降到约 12.5 ms。

完整原生 Skia 追踪本身有开销；不带这套追踪的前一组测试同样复现 3～4 FPS。此结果只说明本机、该视口和经典预设的实际瓶颈与干预效果，不能作为所有设备的帧率保证。

正式修复需用逻辑/CSS 缩放选择 LOD，并匹配图集实际像素尺寸；现有 32×32 图集对大体型模型与高缩放有尺寸限制，需要一并处理。简单抬高阈值的诊断开关尚未作为正式实现合入。

## 3. Worker 还有另一个独立的模拟瓶颈

在同一真实浏览器中，开启战斗：

| 条件 | FPS | 模拟单步平均/P95 | 实际模拟倍速 |
| --- | ---: | ---: | ---: |
| DPR 1.5，原矢量路径 | 3.6 | **102.5 / 115.7 ms** | 0.47× |
| DPR 1，原缓存路径 | 58.2 | **98.4 / 105.2 ms** | 0.49× |
| 诊断开关暂停所有绘制提交 | 120.2 | **83.9 / 93.7 ms** | 0.56× |

三个运行窗口依次推进，战况和伤亡略有变化，不用它们计算严格的模拟提速比例。它们共同证明：恢复显示帧率后，模拟仍达不到 20 Hz 所要求的 50 ms/步。

前轮 111 ms 数字来自 Node/Vite SSR；本轮打包后的 Node 模拟接战窗口约 84～87 ms，真实浏览器 Worker 约 98 ms。**用 SSR 数字直接代表游戏实际 Worker 不准确，本轮浏览器数据优先。**

真实 Worker 的 12 秒 CPU 采样（DPR 1 缓存路径）：

| 调用子树 | 占采样窗口 | 含义 |
| --- | ---: | --- |
| `step` | 93.3% | 几乎所有 Worker 时间用于模拟 |
| `moveSoldiers` | **43.6%** | 个人移动、选敌、转向、绕行 |
| `resolveMelee` | **24.3%** | 近战接触、目标与遮挡 |
| `separate` | **12.3%** | 碰撞分离 |
| `nearestEnemy` | **22.9%** | 多个阶段重复调用，部分属于上列阶段 |
| `chargeAt` | **19.5%** | 对目标整队逐兵扫描 |
| `Spatial.query` | **15.2%** | 网格查询，分散在不同阶段 |
| `gapBetween` | **12.1%** | 逐候选的身体间距计算 |

这些含子调用的条目有嵌套和交叉，不能把整张表相加。`moveSoldiers`、`resolveMelee`、`separate` 这三个独立阶段合计约占整个采样窗口 80%。Worker 消息打包/发布与主线程 `applyFrame` 没有进入主要热点。

## 4. Profile 已进一步落到具体热点代码行

**全目标扫描及距离计算。** `src/sim/battle.ts:930` 每个攻击兵模遍历目标整队；其中 `Math.hypot(foe.x-s.x, foe.y-s.y)` 是 `chargeAt` 最热代码行，浏览器采样有 932 个行 ticks，远高于下一行拥挤/Map 查询的 181 个。距离过远、应继续列队的判断放在全扫描之后，尚未接近时也支付代价。人数翻倍会同时增加攻击者与目标人数，形成平方增长。

**先算角度，再排除远处候选。** `src/sim/battle.ts:1363` 对待命士兵的候选先做 `atan2` 和 `angDiff`，后面才计算身体间距。该角度行有 523 个 ticks，是 `nearestEnemy` 最热代码行。方形网格查询出来的许多候选最终不在有效接敌距离内。

**通用 hypot 用在高频二维距离内。** `src/sim/formation.ts:45` 圆形身体间距的 `Math.hypot(...)` 几乎占了 `gapBetween` 的全部行采样：1,376 ticks。大量热点不是复杂机制本身，而是在重复候选上反复进行开方、通用 hypot、三角函数和对象访问。

**查询数组与去重开销。** `src/sim/spatial.ts:70` 左右的 seen-token 检查、候选循环和 `out.push` 为查询热点；经典预设全部圆形时，每个模型只插入一个点，仍走为多点胶囊准备的通用去重。独立验证表明单独去重快路径收益较小，它不是主要解法。

**嵌套遮挡查询。** `src/sim/battle.ts:1459` 的 `meleeScreened` 为每个有效接触候选再次查网格、创建形状点、计算射线相交；它在冷却期间也重复执行。前轮 13% 实验只覆盖这里的一部分，不能代表整体可优化空间。

## 5. 用独立内核实验验证热点成本

统一从冻结的第 20 秒状态恢复；每个变体先预热 100 步，再测量 100 步。基线在实验前后各跑一遍，减少执行顺序/机器温度的误判。这里是纯模拟相对实验，未同时运行浏览器负载。

| 变体 | 平均 ms/步 | 与前后基线均值比较 |
| --- | ---: | ---: |
| 基线 A / B | **98.35 / 100.69** | — |
| 二维 `hypot` 改为局部平方和开方 | **75.08** | 约 −24.6% |
| 角度检查前按平方距离排除远候选 | **88.68** | 约 −10.9% |
| 确认单点插入时跳过去重 | **95.57** | 约 −4.0% |
| 三项组合 | **67.80** | 约 −31.9% |

距离粗筛和单点网格实验的结束状态 SHA-256、后续随机数与基线完全一致。快速距离及组合实验的浮点状态哈希不同，后续随机数一致，所有诊断异常列表为空。**浮点计算替换并非逐位等价，此处仅用于证实成本来源，尚未作为已验收机制优化合入。** 这组试验只覆盖一个种子和 5 秒接战窗口，不能替代机制回归。

组合后仍超过 50 ms，因此下一步模拟优化应减少实际候选数量、合并邻域查询、提前粗筛全目标扫描；单纯换几个数学调用仍不足以完成最大规模满速目标。

## 处理优先级

1. **先修 DPI/LOD/图集路径。** 本机已用同一暂停画面证明 3.3→58 FPS，这是导致“PPT”的直接问题。
2. **让性能面板报告实际帧间隔与模拟/墙钟速度，并明确 render 仅为 JS 提交耗时。** 当前面板容易把 20 ms 的提交误读成完整渲染只花 20 ms。
3. **处理选敌候选规模与近邻筛选顺序。** 这是打包 Node 与真实 Worker 两组 profile 共同指向的主要模拟热点。
4. **再处理遮挡复验、邻接复用与碰撞活动集合。** 四轮碰撞并非唯一大头，整体重写碰撞或增加 Worker 数量之前应先降低重复工作。
