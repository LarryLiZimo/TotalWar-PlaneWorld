# 最大规模预设会战性能调查（2026-11-04）

后续已补充真实浏览器主线程/Worker CPU profile 与 GPU/Skia Trace，并在同一暂停画面实测 DPI 缓存路径为 3.3→58 FPS。以[深度 Profile 报告](profile-deep-2026-11-04.md)的浏览器证据为准；本报告中的 SSR 模拟时间和 Canvas 调用计数保留为先前诊断记录。

最大规模的卡顿有两条独立原因：**模拟的计算量超过实时预算；显示层还可能因为屏幕缩放关闭已有的精灵缓存。** 本次只在 `scratch/perf-investigation` 的冻结代码副本内测量和实验，正式源码未作修改，便于与同时工作的 Agent 避免冲突。

## 实测结论

固定种子 `20261104`、经典步射对经典步射、8×，共 **6,368 个模型**；仅北军按现有逻辑自动下令，玩家未操作。Node `v22.15.1`，固定模拟步长 0.05 秒。测量前 40 秒，并单独观察接战后的 20～40 秒。

| 测量 | 接战后平均每步 | 意义 |
| --- | ---: | --- |
| 原始模拟，无计数插桩、无绘制 | **111.45 ms** | 一倍速预算为 50 ms；纯模拟吞吐上限约 0.45× 实时 |
| 原始模拟，阶段计时、查询计数和 CPU 采样 | 127.27 ms | 用于定位热点，插桩有额外开销 |
| 独立实验：省去不需要选攻击目标时的遮挡检查 | **97.12 ms** | 同一窗口耗时减少约 **12.9%**，仍超过 50 ms 预算 |

默认组合的最大规模也有同类问题：经典步射对重装推进、8× 共 5,680 模型，插桩后 20～40 秒平均 116.30 ms/步。

这些是无界面模拟测量，**不能当作浏览器 FPS**。另一 Agent 在同时工作，绝对时间会受到机器负载影响；测量使用独立副本，避免运行中加载不同版本源码。调查期间检测到正式 `src/sim/units.ts` 有并行修改，本报告对应冻结时的兵种数据。完整源文件 SHA-256、分段原始测量及实验结果见 [JSON 报告](performance-investigation-2026-11-04.json)。

## 1. 屏幕缩放可能关闭精灵缓存，放大绘制负担

代码路径：`src/main.ts:67` 按 `devicePixelRatio` 放大画布，`src/main.ts:417` 用画布物理尺寸适配镜头；`src/render.ts:379` 仅在 `camera.zoom <= 4` 时使用缓存。因此，同样的 CSS 视野在较高 DPI/浏览器缩放下，会被当成“近景”，回退到每个兵模分别绘制矢量图形。

对同一初始战局、1600×900 CSS 画布，用模拟 Canvas 上下文统计实际走过的 API 调用：

| DPR | 初始 camera.zoom | 精灵缓存 | 主画布 API 调用/帧 |
| --- | ---: | --- | ---: |
| 1 | 3.44 | 开 | **6,779**，其中 6,368 次 drawImage |
| 1.25 | 4.30 | 关 | **127,179** |
| 1.5 | 5.17 | 关 | **127,179** |
| 2 | 6.89 | 关 | **127,179** |

这约为 **18.8 倍 API 调用数量**，不是 18.8 倍耗时或 FPS 差异。计数不包括属性赋值，缓存生成调用单独记录。它证明缓存确实会在相同视野下被 DPI 关闭；本轮没有新测浏览器栅格化、合成或 GPU 时间，也没有确认用户当前窗口的 DPR。

优先修正方向：用逻辑/CSS 缩放决定表现细节，并为实际物理像素大小匹配图集格子。现有图集格子固定 32×32，扩大缓存适用范围时需要同时处理武器、骑乘模型的尺寸与裁切。缩放每次变化还会清空整个图集（`src/render.ts:380`），连续滚轮缩放也可能造成重建尖峰。

## 2. 逐兵选敌存在按编制人数平方增长的扫描

`src/sim/battle.ts:914` 的 `chargeAt` 对每个攻击兵模遍历目标整队，计算距离、拥挤程度、选敌代价。**是否仍在放手距离之外的判断，放在整队遍历之后**，所以相距很远时也支付这笔费用。

相同战斗的 5～10 秒窗口，尚无伤亡：

- 4×：每步 1,320 次选敌，共扫描 **158,400** 个目标槽位。
- 8×：每步 2,640 次选敌，共扫描 **633,600** 个目标槽位。

人数翻倍，目标扫描量变成四倍；按目标 20 Hz 计算，仅这条路径就要求每秒约 1,267 万次候选遍历。当前空间网格没有用于缩小这段目标整队扫描。

优化方向：先用目标实际身体包围范围作距离粗筛；近距离再按空间索引检索候选，并减少重复选敌。整队已经投入战斗时，仍需支持远处预备兵寻找目标，不能简单限制一个很小的固定查询半径。`crowdOn` 有步内缓存及顺序依赖，修改筛选顺序也需要验证行为。

## 3. 接战后重复的邻域与遮挡检查占据主要时间

最大经典对战 20～40 秒的插桩阶段平均值：

| 阶段 | ms/步 | 占总步长 |
| --- | ---: | ---: |
| 个人移动、近敌查询、选敌、绕行 | **50.61** | 39.8% |
| 近战接触、攻击区域、攻击遮挡 | **35.80** | 28.1% |
| 碰撞分离 | **24.85** | 19.5% |
| 冲锋/疲劳/接战后处理 | 6.31 | 5.0% |
| 射击 | 4.19 | 3.3% |
| 士气 | 3.00 | 2.4% |

同一窗口每步平均约 **48,578 次空间查询、337 万个网格候选条目访问、8 次网格重建、4 轮碰撞分离**。空间网格已经存在；问题在于同一批邻居被不同系统反复查询和计算。

CPU 采样中，`Spatial.query` 含子调用约占 23.3%，`nearestEnemy` 约 21.2%，`chargeAt` 约 17.1%，`meleeScreened` 约 10.4%。这些是包含子调用的比例，存在重叠，不能相加。GC 自身约占 3.4%，目前应优先减少重复工作。

主要位置：

- `src/sim/battle.ts:1346`：个人移动时查询近敌；后续近战和受阻判定再次查近敌。
- `src/sim/battle.ts:1386`：即使模型仍在冷却或已有挥击，仍对接触候选重复做攻击区域和遮挡筛选。
- `src/sim/battle.ts:1459`：一次攻击遮挡判断会再次查网格、遍历附近模型、构造形状点。
- `src/sim/battle.ts:1820`：分离每轮重建网格，再为所有存活模型查邻域；混战中基本跑满四轮。
- `src/sim/spatial.ts:49`：查询返回覆盖方形范围的网格候选，后续才筛距离、阵营及目标；很多查询先取出了大量同阵营模型。

优化方向：按用途/阵营组织查询，复用合法的邻接信息，减少对非接战模型的查询；碰撞用活动接触集合与局部更新减少全场重复扫描。网格重建之间有模型移动，直接删除重建可能漏碰撞；减少分离轮数也会改变接触刚度、穿行与战车挤出，需要专项回归。

## 4. 独立实验验证了一项可减少的重复计算

在 `resolveMelee` 保留接触、侧背压力、投入战斗标志等更新，仅在以下条件下继续寻找用于起手/冲锋的攻击目标：

```ts
s.chargeArmed || (!s.swing && s.meleeCd <= 0 && reg.order !== 'move')
```

其他情况下，跳过该轮攻击区域/攻击遮挡筛选；前摇结束时的命中与遮挡复验保持原逻辑。这个改动只存在于实验副本。

同种子和编制各跑 800 步（40 模拟秒），每 5 秒对完整可序列化战斗状态作 SHA-256 比较，8 个检查点全部相同；结束后连续 32 个随机值也一致；两次诊断异常列表均为空。20～40 秒平均从 111.45 降至 97.12 ms/步，减少约 12.9%。

这验证了重复检查确实有实际成本，但只覆盖一个种子、一个编制、前 40 秒。若落入正式实现，还需检查冲锋、前摇、溅射、转攻和移动脱离等原有回归；本次没有把实验改动合并到正式源码。

## 5. Worker 和插值无法弥补模拟吞吐不足

`src/sim/battle.worker.ts:38` 每次仍串行执行完整 `step`。循环的 8 ms 限制在一次 `advance()` **之后**检查，无法切开一个 111 ms 的模拟步。发布间隔“至少 1/30 秒”也不会使消息达到 30 Hz：计算速度只有约 9 步/墙钟秒时，运动状态更新也相应变稀。

`PoseHistory` 能平滑收到的状态，但无法让运算受限的 0.45× 战局恢复一倍速。其至少约 100 ms 的显示缓冲还会叠加感知延迟。主线程同时受到高 DPI 矢量绘制拖累时，就会同时出现画面掉帧、战斗变慢和命令反馈迟缓。

已有浏览器记录 `reports/browser-army-stress-after.json` 的 39 FPS、模拟 122.9 ms、绘制提交 18.6 ms 属于此前窗口，仅作辅助证据；没有将它与本次无界面测量合并计算提速比例。

## 建议处理顺序

1. 修正 DPI/缩放导致的缓存失效；以相同 CSS 视野在 DPR 1/1.25/1.5/2 下验证，并记录真正的浏览器长帧和绘制耗时。
2. 将已验证的近战目标筛选门槛做成正式改动，跑机制回归和多种子对照。
3. 消除远距离逐兵全目标扫描，降低同一步内重复的敌我邻域查询；继续以最大预设的接战阶段采样。
4. 再优化碰撞活动集合、缓存与数据布局。当前这些热点已有清楚的算法原因，可据此衡量是否还需要渲染或模拟架构迁移。

验收应同时记录显示帧 P95、模拟步 P95、墙钟/模拟时间比，并覆盖开场、接战、持续混战及多队转攻。最大规模还需至少约两倍的模拟提速才能接近一倍速，单项约 13% 的实验收益尚不足以达标。
